This Epic contains six features:

- Feature-001 — Page Links title and spacing.

Continue using the existing architecture:

Read and follow `AGENTS.md`.

Preserve all existing functionality from Epics 001–007.

# Feature-006 — Reusable Colour-Aware Buttons

**Status:** not started

## Objective

Create a reusable React button component that automatically uses colours appropriate to the section in which it is placed.

It should support two variants:

- Primary Button.
- Secondary Button.

The existing Contact Us form Submit button must use the Primary variant.

## 1. Shared Button Component

Create a reusable React button component.

Suggested name:

`AlohaButton`

Use the project's existing React component conventions.

Requirements:

1. Use a single shared component for Primary and Secondary buttons.
2. Support standard button behaviour.
3. Support accessible labels and keyboard interaction.
4. Support relevant button types such as `button` and `submit`.
5. Support disabled states where required.
6. Allow children or text content without hardcoding labels.
7. Preserve existing functionality of any button converted to use this component.
8. Do not introduce an unnecessary third-party button library.

Use semantic `<button>` markup.

Do not create a Gutenberg block for this feature unless an actual editor requirement makes it necessary.

## 2. Colour Awareness

The button should automatically apply an appropriate colour scheme based on the background of the section containing it.

The existing Aloha Academy colour groups include:

- Green Group.
- Light Blue Group.
- Cream Group.
- Grey Group.

There is also the additional global Dark Green colour.

### Requirements

1. Use the existing global SCSS design tokens.
2. Determine the appropriate button colours from the parent section's existing theme/colour-group information.
3. Avoid requiring developers to manually specify text, background and hover colours every time.
4. Preserve readable contrast.
5. Avoid choosing colours based on unreliable sampling of rendered background pixels.
6. Prefer the existing theme context, CSS class or `data-*` attribute system.
7. Provide a sensible default when no recognised theme is supplied.
8. Ensure nested elements retain the correct button colour treatment.

Where possible, both variants should inherit their palette automatically from the same shared system.

### Example

A button inside the Green Contact Us section should use an appropriate contrasting appearance based on the site's established Green Group colours.

A button placed in a Cream section should automatically use an appropriate contrasting Green-based appearance.

Do not invent a completely separate button colour palette.

Use the existing site's approved colour combinations, and verify text contrast against the button background.

## 3. Primary and Secondary Variants

Create a variant property.

Suggested API:

```jsx
<AlohaButton variant="primary">
  Submit
</AlohaButton>

<AlohaButton variant="secondary">
  Clear
</AlohaButton>
```

The primary distinction between variants is their size and hover behaviour.

Both variants should use the same theme-aware colour system.

### Primary Button

- More vertical padding.
- More prominent appearance.
- Suitable for primary actions such as form submission.

### Secondary Button

- Less vertical padding.
- More compact appearance.
- Suitable for supporting actions.

Use consistent horizontal spacing, typography, border treatment and corner radius unless the hover behaviour requires otherwise.

## 4. Minimum Width

Both variants must use:

```scss
min-width: 160px;
```

Requirements:

1. Minimum button width is 160px.
2. Add sufficient horizontal padding.
3. Longer Japanese and Latin labels must fit naturally.
4. Allow buttons to become wider than 160px.
5. Avoid clipping or overflowing text.
6. Keep buttons responsive on narrow screens.
7. Do not force every button to exactly 160px.

Use an appropriate width constraint so a button can shrink safely within a narrow mobile container where necessary.

## 5. Primary Button Hover Animation

The Primary button should reuse the existing navigation hover effect.

The effect consists of:

1. Text moves upwards slightly.
2. A decorative wave animates into view from the bottom.
3. The wave moves behind the text.
4. The button's outer dimensions remain unchanged.

### Requirements

- Reuse the existing navigation hover-wave implementation or shared animation utilities.
- Preserve the established motion style and timing.
- Keep the text above the wave layer.
- Ensure the wave never obscures the label.
- Clip the wave to the button's boundaries.
- Keep the button height unchanged during hover.
- Avoid any layout shift.
- Ensure the wave's colours are appropriate to the button's current theme.
- Restore the original state when the pointer leaves.

The hover animation should closely match the existing desktop navigation effect.

Do not approximate it using an unrelated animation when the existing effect can be reused.

### Text Movement

Move the text upwards slightly through a transform.

Do not change margins, padding or line-height to achieve the movement.

The button itself must not grow taller.

## 6. Secondary Button Hover Animation

The Secondary button should use a simpler hover treatment.

When hovered:

1. The button background becomes darker.
2. The entire button moves upwards slightly.
3. Both effects animate smoothly.
4. The button returns to its original position when hover ends.

Requirements:

- Use an appropriate darker colour from the current theme.
- Maintain sufficient text contrast.
- Use a small negative `translateY` value.
- Do not change the document layout or surrounding spacing.
- Do not use the Primary button's wave animation.
- Preserve a clear focus state.

## 7. Keyboard and Touch Behaviour

Both variants must remain accessible.

Requirements:

1. Use semantic buttons.
2. Preserve keyboard activation.
3. Show a visible keyboard focus indicator.
4. Do not rely on hover alone to communicate functionality.
5. Maintain sufficiently large touch targets.
6. Respect `prefers-reduced-motion`.
7. Disabled buttons should not trigger hover animations.
8. Preserve existing form submission behaviour.

Do not introduce unnecessary loading animations or new validation logic.

## 8. Update Contact Form Submit Button

Refactor the existing Contact Us Submit button to use the new shared component.

It must use:

```jsx
<AlohaButton variant="primary" type="submit">
  Existing submit label
</AlohaButton>
```

This is illustrative; preserve the actual Japanese text already used by the form.

Requirements:

1. Use the Primary variant.
2. Inherit the appropriate colours from the Green Contact Us section.
3. Preserve the existing button label.
4. Preserve form submission.
5. Preserve validation behaviour.
6. Preserve disabled/submitting states.
7. Preserve WordPress REST API integration.
8. Preserve FluentSMTP functionality.
9. Preserve spam protection and error handling.
10. Do not cause duplicate submissions.

The form's underlying logic must remain unchanged.

Other buttons, such as the message-clear action, should not be changed unnecessarily unless sharing the new component is straightforward and preserves their existing intended appearance and behaviour.

## 9. Reusability

The component should be easy to use in future React components.

For example:

```jsx

  お申し込み
</AlohaButton>
```

Theme-aware colour selection should work without manually passing individual colour values.

Do not refactor every existing website button as part of this feature.

Implement the reusable component and migrate the Contact Us Submit button only.

## Acceptance Criteria

- Shared React button component exists.
- Primary and Secondary variants work.
- Colours adapt to existing section colour groups.
- Text contrast remains appropriate.
- Minimum width is 160px.
- Longer text can expand the button.
- Primary has greater vertical padding.
- Secondary has tighter vertical padding.
- Primary hover reuses the navigation wave.
- Primary label moves upwards without changing button height.
- Secondary hover darkens the background and moves the button upwards.
- Both animations reverse smoothly.
- Reduced-motion support works.
- Focus and disabled states remain functional.
- Contact Us Submit uses the Primary variant.
- Contact form submission and validation remain unchanged.
