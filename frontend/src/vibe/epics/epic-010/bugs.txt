## Bug-001 — Prevent Animated Water Waves from Stretching Vertically

**Status:** complete

**Notes:** Page Links and Classes used a fixed 600-unit SVG viewBox scaled to the container height. The viewBox now follows the rendered height, keeping the animated SVG patterns at a fixed vertical scale and tiling them across the full background. Build and browser checks passed at all six widths, with changing link counts, 400–1,200px test heights, running animation and reduced motion.

### Issue

The animated water background used in the Page Links section and Classes Hero does not behave correctly on mobile.

When these sections become taller, particularly because their circular links stack vertically, the background waves become vertically stretched.

I want the waves to retain their original height and proportions regardless of how tall their parent section becomes.

If the container becomes too tall for the existing waves to cover, additional waves should be generated or repeated to cover the remaining background.

### 1. Preserve Wave Height

Inspect the existing shared animated water background.

Identify why wave height changes when the parent container becomes taller.

Pay particular attention to:

- SVG dimensions and `viewBox`.
- `preserveAspectRatio`.
- CSS `background-size`.
- Percentage-based element heights.
- SVG or container transforms.
- Absolute positioning.
- Shared background sizing calculations.

Requirements:

1. The individual animated waves must retain a consistent vertical height.
2. Increasing the parent section's height must not stretch the waves.
3. Reducing the parent section's height must not squash them.
4. Preserve the existing wave curvature and proportions.
5. Preserve the existing wave colours.
6. Preserve existing animation speeds and movement.
7. Keep the waves responsive horizontally.
8. Do not tie their vertical size to `height: 100%` when that causes distortion.

The animated water should maintain the same visual wave height whether its container is 400px or 1,200px tall.

### 2. Generate Additional Waves When Necessary

When the parent section becomes taller, the water background must continue filling its entire height.

Requirements:

1. Determine the available background height.
2. Maintain a consistent height for individual wave bands.
3. Repeat or generate additional wave bands when necessary.
4. Cover the entire section without leaving empty areas.
5. Allow the number of visible wave bands to adapt to the section's dimensions.
6. Prevent visible seams between repeated waves.
7. Avoid abrupt changes in wave positioning when the layout resizes.
8. Preserve the current organic wave appearance.

For example, if a background previously contained enough waves to cover 500px and the section becomes 1,000px tall, add enough wave coverage rather than stretching the existing waves to twice their height.

### 3. Reuse the Existing Water Background Component

The website already uses a shared animated water background.

It is currently used in:

- Homepage Hero.
- Page Links.
- Classes Hero.

Requirements:

1. Fix the shared implementation wherever appropriate.
2. Preserve the existing Homepage Hero appearance.
3. Ensure the Page Links and Classes Hero use the corrected background.
4. Do not create independent wave systems for each section.
5. Avoid unnecessary duplication of animated SVGs or React components.
6. Preserve the swimming turtle integration.

If the Homepage Hero requires its existing wave geometry or sizing to remain unchanged, use a suitable shared configuration rather than changing its appearance unintentionally.

### 4. Preserve Animation

Additional wave bands must participate in the existing water animation.

Requirements:

1. Preserve the current horizontal wave movement.
2. Preserve the current animation timing.
3. Avoid static-looking gaps between animated regions.
4. Prevent waves from visibly jumping when repeated.
5. Ensure animation remains continuous during scrolling.
6. Avoid unnecessary React updates on every animation frame.
7. Respect `prefers-reduced-motion`.

Prefer efficient CSS/SVG background tiling or another approach compatible with the existing animation system.

Do not generate large numbers of unnecessary DOM elements.

### 5. Responsive Behaviour

This issue is particularly noticeable on mobile because the circular links become vertically stacked.

Verify that the background adapts when:

- Four links are on one row.
- Links collapse into two columns.
- Links collapse into one column.
- The section height changes after content loads.
- The viewport is resized.
- WordPress links are added or removed.

Requirements:

1. All section backgrounds remain completely covered.
2. Wave height stays consistent.
3. No vertical stretching.
4. No exposed background gaps.
5. No horizontal overflow.
6. No layout shifts caused by adding wave bands.

### 6. Preserve Existing Functionality

Do not change:

- Page Links content.
- Page Links heading.
- Circular link styling.
- Link entrance animations.
- Hover animations.
- Classes Hero heading.
- Classes Hero bottom wave.
- Classes Hero anchor navigation.

**Important:** This bug concerns the animated waves inside the water background, not the decorative wave-shaped boundaries between page sections.

Do not unnecessarily modify those section boundaries.

### Acceptance Criteria

## Bug-002 — Correct Testimonials Background Image Scaling on Mobile

**Status:** complete

**Notes:** Testimonials shared the desktop divider overscan on mobile. The shared hook now fits the image to the larger of section width and 150% of section height at widths through 899px, with movement clamped to the available height. Desktop geometry and the wave mask remain in use, and the image-only overlay uses the specified 0.2 opacity. Eight tests and local browser checks passed across all six widths and three image aspect ratios.

### Issue

On mobile, the Testimonials section does not size its background image correctly.

The image should scale down appropriately to match the viewport width while maintaining enough image height for the existing parallax scrolling effect.

I want the image to be as small as reasonably possible while still covering the visible section and providing additional space above and below for parallax movement.

### 1. Required Image Coverage

The background image must cover:

- The full width of the Testimonials section.
- The full height of the Testimonials section.
- An additional 25% of the section's height above.
- An additional 25% of the section's height below.

This gives the image enough vertical space to move during parallax scrolling.

If the section height is H, the target image height must be at least:

```text
Required image height = H × 1.5
```

For example:

If the Testimonials section is 600px tall:

- Visible section: 600px.
- Additional space above: 150px.
- Additional space below: 150px.
- Minimum rendered image height: 900px.

The image should remain vertically centred at the neutral parallax position.

### 2. Prioritise Viewport Width When Possible

On mobile, first determine whether the image can be displayed at the width of the page.

If scaling the image to the viewport width produces sufficient height for the parallax requirement, use that size.

For example:

```text
Viewport width: 375px
Scaled image height: 1000px
Required image height: 900px

Result: Use 375px image width.
```

This prevents unnecessary horizontal enlargement or cropping.

### 3. Increase Image Size Only When Necessary

If displaying the image at viewport width does not produce enough height, increase the image's size proportionally until the minimum required height is satisfied.

For example:

```text
Viewport width: 375px
Scaled image height: 500px
Required image height: 900px

Result: Increase image scale until height is 900px.
```

This may result in the rendered image being wider than the viewport, with the excess width cropped by the container.

That is acceptable when necessary to maintain image coverage and parallax movement.

### 4. Image Scaling Calculation

Use the image's intrinsic dimensions and the section's actual dimensions.

Let:

- W = container width.
- H = container height.
- IW = original image width.
- IH = original image height.

The minimum scale factor should satisfy both width and vertical coverage:

```js
const requiredHeight = containerHeight * 1.5;

const scale = Math.max(
  containerWidth / imageWidth,
  requiredHeight / imageHeight
);

const renderedWidth = imageWidth * scale;
const renderedHeight = imageHeight * scale;
```

This is an illustrative calculation.

Adapt it to the existing image-rendering implementation.

Requirements:

1. Preserve the image's original aspect ratio.
2. Never stretch the image independently on either axis.
3. Do not make the image larger than necessary.
4. Ensure the rendered width covers the section.
5. Ensure the rendered height accommodates parallax movement.
6. Centre the image horizontally.
7. Keep the image vertically centred at the neutral parallax position.

### 5. Preserve Parallax Behaviour

The Testimonials background should continue using the existing Image Divider-style parallax effect.

Requirements:

1. Preserve the existing scroll-based movement.
2. Preserve the neutral midpoint alignment.
3. When the section centre aligns with the viewport centre, the image should be vertically centred.
4. As the user scrolls down, the image should move smoothly upwards.
5. Use the available vertical overscan safely.
6. Never expose the image's straight top or bottom edge.
7. Keep the image behind the organic wave boundaries.
8. Preserve reduced-motion behaviour.

The 25% additional image height on each side should be available for the parallax effect, rather than being removed through incorrect positioning or clipping.

Clamp the actual movement to the available safe overscan if necessary.

### 6. Account for Responsive Section Height

The Testimonials section displays:

- Three testimonials on desktop.
- Two on intermediate screens.
- One on mobile.

Its height may change depending on the number of visible cards and the length of their text.

Requirements:

1. Use the section's actual rendered height.
2. Recalculate image sizing when the section height changes.
3. Recalculate on viewport resizing.
4. Recalculate when the background image changes.
5. Avoid repeated layout calculations during every scroll frame.
6. Preserve the carousel's existing responsive layout.
7. Prevent sudden image-size jumps during carousel movement.

Use existing measurement utilities or ResizeObserver where appropriate.

### 7. Preserve Wave Borders and Overlay

The Testimonials section already has:

- Top wave boundary.
- Bottom wave boundary.
- Black image overlay at 0.2 opacity.

Preserve all three.

Requirements:

1. Keep the background image correctly positioned beneath both waves.
2. Keep the overlay covering the visible image.
3. Do not apply the overlay to testimonial cards.
4. Prevent straight image edges from appearing through the wave masks.
5. Prevent exposed white or transparent gaps.
6. Preserve transitions into neighbouring sections.

### 8. Preserve Desktop Behaviour

This is primarily a mobile sizing correction.

Do not unnecessarily change the existing desktop parallax effect or image presentation.

The corrected sizing logic may be shared with desktop if it preserves the current appearance.

### 9. Preserve Existing Testimonials Functionality

Do not modify:

- Carousel timing.
- One-testimonial-at-a-time movement.
- Card shapes.
- Card staggering.
- Card colours.
- Quote and name typography.
- Existing entrance transitions.
- Automatic scrolling.
- Hover behaviour.
- WordPress image selection.
- WordPress testimonial editing.

### Acceptance Criteria

- Mobile image is scaled appropriately to the viewport.
- Image is no larger than necessary.
- Image covers the full section width.
- Image extends at least 25% of section height above and below at neutral alignment.
- Original image aspect ratio is preserved.

## Bug-003 — Reduce In-Page Loading Time and Skip Cached Loads

**Status:** complete

**Notes:** In-page routes shared the three-second minimum and fetched content on every mount. They now use a 500ms minimum plus the existing 500ms fade and bypass the loader for successful page data cached for the current app session. Failed or canceled requests do not enter the cache. Chrome verified the initial three-second overlay, fast and slow loads, retry, cache, scroll reset, anchor navigation and cancellation.

### Issue

The website currently has two loading screens:

1. A full-screen loading screen displayed while the website's navigation is initially loading.
2. An in-page loading screen displayed when navigating to another page and waiting for its content.

Both currently use a minimum display time of three seconds.

I want to keep the initial website loading screen unchanged.

However, the in-page loading animation should appear for a much shorter time.

If the destination page is already available in the application's cache, I would prefer not to show the in-page loading animation at all.

### 1. Preserve Initial Website Loading Screen

Do not change the initial site-loading overlay.

It must continue to use:

- Dark Blue full-screen background.
- Light Blue Shaka.
- Light Blue 読み込み中 text.
- Shaka width up to 400px.
- Existing shake animation.
- Minimum three-second full display.
- Half-second fade-out.

Minimum total lifetime remains approximately 3.5 seconds.

This loading screen is independent of the changes described below.

### 2. Reduce In-Page Loading Minimum

The in-page page-content loading screen should have a minimum display time of:

**0.5 seconds (500ms)**

Requirements:

1. Show the loading screen when the destination page content is genuinely pending and cannot be rendered immediately.
2. Once displayed, keep it fully visible for at least 500ms.
3. If content takes longer than 500ms, continue displaying it until content is ready.
4. Do not begin the fade-out until both the minimum time and content-readiness conditions are satisfied.
5. Do not preserve the previous three-second minimum for in-page loading.
6. Keep the initial full-screen loading overlay's timing unchanged.

### 3. Preserve Fade-Out

The in-page loader should still fade out smoothly.

Use the existing:

**0.5-second fade-out**

Requirements:

1. Fade the loading content out over 500ms.
2. Avoid abrupt removal.
3. Do not briefly display a blank section between loading and content.
4. Prevent duplicate fade transitions.
5. Remove loading elements from the layout when finished.
6. Restore normal page interaction.

When displayed, the in-page loader's minimum total lifetime should therefore be approximately:

**1 second**

- 0.5 seconds fully visible.
- 0.5 seconds fading out.

If the actual content fetch takes longer, the loading screen should remain until it is ready.

### 4. Skip Loading Screen for Cached Pages

When navigating to a page whose required content is already available in the application's cache, show the page immediately.

Requirements:

1. Inspect the existing page-content caching system.
2. Detect whether usable content for the destination route is already available.
3. If the data is available immediately, render the destination page without displaying the in-page loader.
4. Do not impose the 500ms minimum when the loader was never shown.
5. Do not fade in or fade out a loading screen that was not displayed.
6. Do not show an empty loading frame before cached content appears.
7. Preserve the existing page content and React component structure.

### Important

Do not assume browser HTTP caching automatically guarantees that React has synchronously available page data.

Use the application's actual route/data cache or existing data state.

The loader should be skipped only when the destination content can genuinely be rendered immediately.

If the data is not ready, show the normal shortened loading screen.

### 5. Avoid Loading-Screen Flashing

Pay attention to transitions where content loads very quickly.

Requirements:

1. Avoid mounting and immediately removing the loader unnecessarily.
2. Check for cached content before committing to the loading state.
3. Once the loader becomes visible, honour the 500ms minimum.
4. Do not repeatedly mount the loader during one page transition.
5. Avoid race conditions between multiple navigation requests.
6. Prevent stale requests from replacing newer page content.

The result should feel smooth regardless of whether page content loads instantly or takes longer.

### 6. Preserve In-Page Loader Appearance

Do not change:

- Dark Blue Shaka colour.
- Dark Blue Japanese loading text.
- Shaka maximum width of 300px.
- Top-centred placement.
- Spacing below the navigation.
- Existing shake animation.
- Normal page background.

When the loader is visible, it should still occupy sufficient height to keep the Contact Us form and Footer below the fold.

Only its minimum display time and cached-page behaviour should change.

### 7. Preserve Navigation and Scroll Behaviour

The website currently returns to the top when navigating between pages.

Requirements:

1. Preserve top-of-page navigation.
2. Preserve the sticky Header.
3. Preserve intentional anchor navigation.
4. Preserve the Contact Us Jump button.
5. Preserve the Home Hero scroll-down button.
6. Do not introduce unexpected scrolling when cached content is displayed.
7. Keep page transitions consistent whether content is cached or fetched.

If navigation targets a specific anchor, honour it after the relevant content is ready.

### 8. Preserve Error Handling

Requirements:

1. Preserve existing loading-error states.
2. Do not leave users stuck on a loader after a request fails.
3. Do not treat failed content as successfully cached.
4. Do not display stale content as current unless this is already an intentional supported caching behaviour.
5. Clean up timers correctly.
6. Preserve existing request cancellation and stale-response protections.

### Acceptance Criteria

- Initial website loading overlay remains unchanged.
- Initial overlay still uses its three-second minimum.
- In-page loader uses a 500ms minimum.
- In-page loader still fades out over 500ms.
- Cached pages render immediately without the loader.
- No loading flash occurs for cached content.
- Uncached pages display the loader correctly.
- Slow requests keep the loader visible until content is ready.
- Loading errors are handled correctly.
- Existing page navigation and anchors work.
- No blank flashes or unexpected layout shifts.
