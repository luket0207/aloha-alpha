# Feature-001 — Remove wp-env Startup Deprecation Warning

**Status:** complete

**Notes:** `npm run wp:start` now starts only the development site and runs without the dual-environment warning on wp-env 12.1.0. The legacy site contained only sample content and has no repository workflow. Verified the original URL, Admin login screen, active theme and plugins, existing pages/patterns/media, and retention of both database volumes.

## Objective

Remove the deprecation warning displayed when starting the local WordPress environment.

The warning states that starting both development and test environments by default is deprecated and recommends separate configurations.

I want the local environment to continue operating as it does now, without displaying this warning.

## 1. Investigate Current Configuration

Inspect:

- `.wp-env.json`
- `.wp-env.override.json`, where present.
- `package.json` scripts.
- The installed `@wordpress/env` version.
- Existing development and test environment configuration.
- Current startup commands.
- WordPress plugin and theme mappings.
- Existing local port assignments.

Determine whether the project currently starts both development and test environments and whether either is required by the existing workflow.

Do not assume the test environment is unused.

## 2. Resolve the Warning Safely

The warning suggests:

```json
{
  "testsEnvironment": false
}
```

However, this option is itself deprecated, and setting it to false can disable the legacy test environment.

Requirements:

1. Use the simplest supported approach for the installed wp-env version.
2. Preserve the existing development WordPress instance.
3. Preserve its existing URL and port.
4. Preserve the existing database.
5. Preserve plugins and theme mappings.
6. Preserve any test environment that is actively required.
7. Do not accidentally replace or recreate existing test data.
8. Remove the deprecation warning from the normal startup workflow.
9. Do not merely suppress or filter the warning text.

If the test environment is not needed, explicitly disabling it may be appropriate.

If both environments must remain available, migrate the startup workflow to the supported separate-configuration approach.

Use a separate test configuration and an appropriate combined startup script where necessary.

If the user's exact existing command cannot retain both environments without the warning, preserve the functionality using a clearly documented replacement command and explain that distinction.

## 3. Preserve Existing Development Environment

Do not:

- Run `wp-env destroy`.
- Run `wp-env reset`.
- Run `wp-env clean`.
- Delete Docker volumes.
- Remove databases.
- Reinstall WordPress unnecessarily.
- Change existing theme or plugin mappings.
- Upgrade packages without a demonstrated compatibility requirement.
- Recreate the project configuration from scratch.

Only change the configuration and scripts necessary to resolve the warning safely.

## 4. Verification

Test the normal startup workflow.

Verify:

1. The warning no longer appears.
2. WordPress starts correctly.
3. The existing development URL is unchanged.
4. WordPress Admin is accessible.
5. AlohaAlpha Core remains active.
6. The existing theme remains active.
7. Existing pages and patterns remain available.
8. Any required test environment remains accessible.

If Docker is unavailable, verify configuration validity and report what remains untested.

## Acceptance Criteria

- The specified deprecation warning is no longer displayed during normal startup.
- Existing development behaviour is preserved.
- WordPress data and plugin mappings are preserved.
- Any required test environment remains usable.
- Startup commands are documented if changed.
- No destructive environment operations are performed.

# Feature-003 — Full-Screen Navigation Loading Screen

**Status:** complete

**Notes:** Added the initial navigation overlay with a shared three-second minimum and half-second fade. It uses the existing Header request and resolves to the existing error state on failure. The live browser check verified readiness, concurrent requests, layout at six widths, reduced motion, and no repeat overlay on client navigation.

## Objective

Introduce a full-screen loading overlay while the website's navigation is being loaded.

I do not want users to see the navigation gradually appearing or displaying incomplete content.

When the site is initially opened, the loading overlay should conceal the entire website until the navigation is ready.

The overlay should also remain visible for a minimum amount of time to prevent flashing.

## 1. Full-Screen Overlay

The loading screen must cover the entire viewport.

Requirements:

1. Cover the entire website behind it.
2. Cover the Header, content and Footer.
3. Use a solid Dark Blue background.
4. Prevent incomplete website content from being visible.
5. Keep the overlay above all normal website elements.
6. Prevent interaction with underlying content while active.
7. Avoid creating additional page height or scrollbars.

Background:

```scss
background: #1B4672;
```

Use the existing Dark Blue token.

The overlay should not depend on the Header's selected colour.

## 2. Loading Content

Display two elements:

1. Shaka SVG.
2. Japanese loading text.

Vertically and horizontally centre these as a single group.

The Shaka should appear above the text.

Use the Japanese label:

**読み込み中**

Requirements:

- Centre the content group in the viewport.
- Maintain comfortable spacing between Shaka and text.
- Use the existing Japanese typography.
- Keep the text centred.
- Do not display the website logo.
- Do not add additional loading messages or progress bars.

## 3. Colours

Use:

- Overlay background: Dark Blue `#1B4672`.
- Shaka: Light Blue `#93B7BE`.
- Loading text: Light Blue `#93B7BE`.

The Shaka should inherit its colour through the existing `currentColor` implementation.

Do not modify the original SVG geometry.

Do not add unwanted outlines or strokes.

## 4. Shaka Dimensions

Maximum Shaka width:

**400px**

Requirements:

1. Use the existing reusable Shaka SVG component.
2. Preserve its aspect ratio.
3. Scale down responsively on mobile.
4. Never exceed the available viewport width.
5. Prevent clipping.
6. Keep the Shaka centred.

The maximum width is 400px, not a mandatory width on small screens.

## 5. Shaka Animation

Reuse the existing Shaka shake animation.

Preserve its established shake movement:

- Resting orientation: −30°.
- Shake between approximately −15° and −45°.
- Four back-and-forth oscillations.
- Shake duration: 1.5 seconds.

However, change the rest interval for the loading screen.

**Loading-screen pause: 0.5 seconds**

Animation sequence:

1. Shake for 1.5 seconds.
2. Remain stationary for 0.5 seconds.
3. Repeat.

The total cycle should be approximately 2 seconds.

Do not globally change the Shaka animation used by other components.

Make the pause duration configurable or use a dedicated animation modifier that reuses the existing shake keyframes.

Respect reduced-motion preferences.

## 6. Loading Completion Condition

The overlay should remain active until the navigation has loaded.

Requirements:

1. Detect when the application's required Header/navigation data has successfully loaded.
2. Do not dismiss the overlay merely because the React application has mounted.
3. Ensure the navigation is ready to render before revealing the website.
4. Include required menu data and other critical Header dependencies in the readiness check.
5. Avoid treating decorative image completion as a prerequisite unless it is essential to the Header's appearance.
6. Do not create duplicate navigation data requests.
7. Avoid race conditions between navigation loading and overlay dismissal.

If navigation loading fails, use the application's established error or fallback behaviour.

Do not leave users trapped behind an indefinite loading overlay.

## 7. Minimum Loading Time

The overlay must remain fully displayed for at least:

**3 seconds**

This minimum begins when the loading screen first appears.

Even if navigation finishes loading immediately, the overlay must remain displayed for the full three seconds.

If navigation takes longer than three seconds, remain visible until it is ready.

The dismissal should begin only when:

- Navigation is ready.
- At least three seconds have elapsed.

Do not restart the minimum timer unnecessarily.

## 8. Fade-Out Animation

After both completion conditions are met, fade out the overlay.

Duration:

**0.5 seconds**

Requirements:

1. Fade the entire overlay from opacity 1 to 0.
2. Keep the website fully concealed until the fade begins.
3. Use a smooth opacity transition.
4. Do not abruptly remove the overlay.
5. Remove the overlay from interaction and rendering after fading completes.
6. Do not leave an invisible element blocking the website.
7. Prevent double transitions.

Minimum total visible lifetime:

**3.5 seconds**, including the fade.

## 9. Preserve Initial Page Loading

Navigation and page content may load concurrently.

Do not unnecessarily force them to load sequentially.

If both navigation and page content are ready when the overlay finishes, reveal the completed page directly.

If navigation is ready but page content is still loading, allow Feature-004's in-page loading screen to appear behind the fading overlay.

Avoid stacking multiple full minimum-duration delays when the underlying loading operations have already been happening concurrently.

## 10. Accessibility and Performance

Requirements:

- Respect reduced-motion preferences.
- Reduced-motion users may see a static Shaka, but should still receive an understandable loading state.
- Provide appropriate loading status semantics.
- Prevent focus from moving into concealed content.
- Restore normal interaction after dismissal.
- Clean up timers.
- Do not introduce polling when existing loading state can be reused.
- Do not re-display this initial navigation overlay for ordinary client-side page changes when the navigation is already loaded.

## Acceptance Criteria

- Full-screen Dark Blue loading screen appears during initial navigation loading.
- No incomplete navigation is exposed.
- Shaka is Light Blue and no wider than 400px.
- 読み込み中 appears beneath the Shaka.
- Shaka shakes for 1.5 seconds and rests for 0.5 seconds.
- Overlay remains fully visible for at least three seconds.
- Overlay waits for navigation readiness.
- Overlay fades out over 0.5 seconds.
- Minimum total lifetime is 3.5 seconds.
- Website becomes interactive after dismissal.
- Loading errors do not permanently block the site.
- Existing navigation and page content remain functional.
