## Bug-004 — Reset Page Scroll Position on Refresh and Navigation

**Status:** complete

### Issue

When refreshing a page or navigating to another page, the website sometimes retains the previous scroll position.

I want each page to start at the top whenever it is freshly loaded or entered through normal page navigation.

### 1. Reset Scroll on Page Refresh

When the browser refreshes the current page:

- The page should return to the top.
- Do not restore the position from before the refresh.
- Do not leave the user halfway down the page.
- Ensure the behaviour is consistent on desktop and mobile.

The expected initial scroll position is:

`window.scrollY === 0`

### 2. Reset Scroll on Route Navigation

When navigating to a different page within the React application:

1. Detect the route change.
2. Reset the scroll position to the top.
3. Ensure the new page starts at its Header/Hero or first content section.
4. Do not retain the previous route's scroll position.
5. Do not briefly reveal the new page at the old scroll position before jumping upwards.
6. Ensure this works across all existing website routes.

Use the existing React routing system rather than attaching arbitrary scroll-reset logic to individual navigation buttons.

### 3. Preserve Intentional In-Page Scrolling

The website already includes buttons designed to scroll to specific sections.

These must continue working.

In particular:

- Home Hero's scroll-down button.
- Contact Us — Jump button.
- Any existing section anchors.

Requirements:

1. Normal navigation to a different page starts at the top.
2. Intentional in-page scrolling must still reach its intended destination.
3. A deliberate URL fragment or anchor destination should be honoured where applicable.
4. Sticky Header offsets must continue to be respected.
5. Do not implement continuous scroll resets that fight against the user's scrolling.

If a navigation action explicitly targets a section on another page, allow the destination route to load before performing the intended section scroll.

### 4. Handle Browser Scroll Restoration

Investigate whether the retained scroll position is caused by:

- Browser scroll restoration.
- React Router navigation behaviour.
- Existing scroll-management hooks.
- Asynchronous WordPress content loading.
- Delayed rendering of components.
- Image loading and layout changes.

Requirements:

1. Identify the existing cause.
2. Implement scroll resetting in the appropriate shared application layer.
3. Use `history.scrollRestoration = 'manual'` if needed, accounting for cleanup and the application's routing behaviour.
4. Avoid conflicting with existing smooth-scroll utilities.
5. Prevent race conditions caused by asynchronous page loading.
6. Avoid repeated or continuous `scrollTo` calls after the user starts interacting with the new page.
7. Preserve browser Back and Forward navigation functionality, while applying the requested top-of-page policy for normal route entries.

### 5. Avoid Unwanted Animation

Returning to the top on refresh or normal route navigation should happen immediately.

Do not smoothly scroll the user from the old position back to the top.

Use instant scrolling for page resets.

Preserve smooth scrolling only for intentional actions such as the Hero scroll-down button and Contact Us Jump.

### 6. Preserve Existing Functionality

Do not interfere with:

- Sticky Header.
- Homepage Hero.
- React routing.
- WordPress page loading.
- Contact Us Jump.
- Scroll-triggered animations.
- Parallax components.
- Testimonials carousel.
- Browser accessibility and focus management.

Ensure scroll-triggered components initialise correctly when a page starts at the top.

### Acceptance Criteria

- Refreshing a page returns to the top.
- Normal navigation to a new page returns to the top.
- Scroll position does not carry over from another route.
- No visible smooth-scroll journey from the old position occurs.
- Intentional in-page navigation still works.
- Contact Us Jump still works.
- Hero scroll-down button still works.
- Sticky Header offsets remain correct.
- React Router and browser navigation remain functional.
- No scroll-position flickering or layout jumps.

**Notes:** Complete. The retained position was native browser history restoration combined with the absence of any React Router-level scroll policy; asynchronous WordPress rendering also meant a simple one-time hash lookup could miss editorial anchors. A shared `ScrollManager` now sets `history.scrollRestoration` to `manual` with cleanup, performs one instant pre-paint reset for every route entry (including Back/Forward), and honours encoded ID or legacy named anchors. Missing hash targets are observed only until they appear or a ten-second limit expires, avoiding repeated resets after user interaction. Two focused tests and the production build passed. Live Chrome checks confirmed home and inner-page refreshes reset from 1400px/615px to zero, all five inner routes plus Back/Forward entered at zero, Hero and Contact intentional smooth scrolling still reached their sticky-header offsets, and `#contact-us` navigation remained honoured.
