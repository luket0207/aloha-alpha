The Shaka should not animate as soon as Contact Us first enters the viewport.

## 4. Shaka — Looping Shake Animation

Once the entrance animation finishes, begin a repeating shake sequence.

### Animation sequence

1. Remain stationary at -30 degrees for 4 seconds.
2. Begin shaking.
3. Rotate repeatedly between -15 degrees and -45 degrees.
4. Complete four back-and-forth oscillations.
5. The shaking movement should last approximately 1 second in total.
6. Return to the resting angle of -30 degrees.
7. Wait another 4 seconds.
8. Repeat.

The movement should feel playful and natural.

Use smooth easing.

The shaking should rotate around the visual centre of the SVG.

Do not rotate the entire Contact Us section or affect other components.

Avoid implementing multiple competing animation systems for the same SVG.

## 2. When the Loading Screen Appears

Show the loading screen:

1. On the initial page load while required content is loading.
2. When navigating to a different page if its required content is not ready.

The loading screen must entirely obscure the page until it is ready.

Do not show partially rendered page content behind it.

## 3. Minimum Display Time

The loading screen must remain visible for at least:

**1,000 milliseconds**

This applies every time the loading screen is shown.

For example:

- Content loads in 200ms → loading screen remains for 1,000ms.
- Content loads in 800ms → loading screen remains for 1,000ms.
- Content loads in 1,500ms → loading screen remains until content is ready.

Do not restart the minimum timer merely because a component re-renders.

Avoid unnecessary flickering.

## 4. Content Readiness

The loading screen should disappear once all critical page content is ready.

Critical content may include:

- The published WordPress page data.
- Shared Header and Footer content.
- Required reusable synced patterns.
- The required Gutenberg-to-React rendering data.
- Large Logo data.
- Essential above-the-fold images needed to display the first screen coherently.

Do not wait for every lazily loaded image farther down the page.

The loading overlay must not become stuck waiting for decorative assets that are not needed immediately.

## 5. Error Handling

If essential content cannot be loaded:

1. Do not display an indefinitely spinning loader.
2. Present an appropriate Japanese error message.
3. Provide an accessible retry control.
4. Avoid exposing internal API details or technical errors to visitors.
5. Do not falsely indicate that the page has successfully loaded.

Ensure failed and stale requests are handled correctly.

## 6. Navigation Behaviour

When navigating between pages:

- Show the overlay if the destination page is not ready.
- Keep it visible for at least 1 second.
- Ensure the new page's required content is loaded before hiding it.
- Ignore stale requests from previous navigation.
- Avoid briefly revealing content from the previous route.
- Do not trigger the loading screen for minor local UI changes or unrelated background activity.

## 7. Accessibility

Requirements:

- Use appropriate loading status semantics.
- Announce the loading state to assistive technologies.
- Block mouse and touch interaction with the underlying page.
- Prevent keyboard interaction with the underlying page while loading.
- Provide accessible error and retry states.
- Respect reduced-motion preferences.
- Avoid flashing or excessive animation.

The loading screen is shared React application UI.

Do not create a Gutenberg block for it.
